Dockerfile入门教程：从零构建你的第一个Docker镜像（含实例）

发表于2026-09-08|更新于2026-10-17|Docker 专题：安装、网络、报错与生产实践
|总字数:4.6k|阅读时长:16分钟|浏览量:

终端里滚动的错误信息——“COPY ../config.json: no such file or directory”。今晚第8次构建失败了。明明本地能跑，一打包成Docker镜像就各种报错。翻遍Stack Overflow，照着top answer改了半天，镜像体积从200MB膨胀到2GB。

看着项目里那个Dockerfile文件，满屏的FROM、RUN、COPY、CMD，每个词单独看都认识，合在一起就是看不懂。网上找教程照着抄，十有八九跑不通。错误提示永远那么模糊——是路径不对？还是指令用错了？

Dockerfile没那么玄乎。后来把每个指令的作用和常见坑都摸清楚了，关键就那么几个点。这篇文章用最直白的方式，从零开始构建第一个Docker镜像。每个指令都配实际代码，还会告诉你初学者最容易踩的3个坑。看完就能给自己的Node.js或Python项目写一个能跑的Dockerfile。

Dockerfile是什么？

简单来说，Dockerfile就是一个文本文件，里面写了构建Docker镜像的所有步骤。你可以把它想象成装修房子的施工图纸——图纸上写明了先铺地板，再刷墙，最后装灯具。Docker引擎按照这份图纸，一步步把你的应用”装修”好，最后打包成一个镜像。

这个镜像就是一个可以直接运行的”环境快照”。比如你的Node.js应用需要Node 18、某些npm包、还有你的源代码，Dockerfile会把这些东西全装进镜像里。别人拿到这个镜像，执行docker run就能跑起来，不用操心环境配置。

说白了，Dockerfile做的事就三步：

  1. 选个基础环境（比如Node.js 18）
  2. 把你的代码和依赖装进去
  3. 告诉容器启动时该执行啥命令

写好Dockerfile后，跑一条docker build命令，镜像就生成了。听起来挺简单？确实不复杂，但魔鬼在细节里。接下来我们聊聊那几个核心指令。

6大核心指令详解

FROM - 选择基础镜像

FROM必须是Dockerfile的第一条指令（除了注释和ARG），它决定了你的”地基”长啥样。

就像盖房子要先选地基，写Dockerfile得先选个基础镜像。你的应用是Node.js写的？那就用node:18-alpine。Python项目？python:3.11-slim是个不错的选择。Nginx做反向代理？直接nginx:alpine。

这里说下alpine和slim的区别。alpine是基于Alpine Linux的超轻量级镜像，体积只有5MB左右，适合生产环境。完整的node镜像有900MB，差了180倍。但alpine有个小坑：它用的是musl libc而不是glibc，个别原生依赖可能会报错。如果遇到奇怪的编译错误，试试换成node:18-slim。

新手常犯错误：随便选了个node镜像，结果版本对不上项目要求，装依赖时各种报错。记住：package.json里写的Node版本是多少，FROM里就用多少。

RUN - 执行命令构建镜像

RUN是在构建镜像时执行命令，用来装软件、创建目录、改配置文件这些活。关键点：每条RUN会创建一个新的镜像层。

这俩指令都是往镜像里复制文件，但COPY简单直接，ADD功能多但容易出幺蛾子。Docker官方建议：能用COPY就别用ADD。

  • 要么在上层目录执行构建：docker build -f myproject/Dockerfile .

WORKDIR - 设置工作目录

WORKDIR就是Linux里的cd命令，设置后续指令的工作目录。如果目录不存在，Docker会自动创建。

推荐用绝对路径，别用相对路径。因为相对路径会基于上一个WORKDIR，容易搞混。

有了WORKDIR，你就不用在每个RUN里写cd /app &&了，代码看起来清爽多了。

再看ENTRYPOINT。它定义容器的主进程，不会被覆盖：

这样组合的话，docker run my-app执行node server.js，docker run my-app script.js执行node script.js。看出区别了吗？ENTRYPOINT是固定的，CMD或docker run的参数会附加到ENTRYPOINT后面。

啥时候用哪个？

  • 只用CMD：应用服务，可能需要不同启动方式（比如生产跑npm start，测试跑npm test）
  • ENTRYPOINT + CMD组合：工具类镜像，主命令固定，只是参数不同（比如Python脚本，主命令是python，脚本名是参数）
  • 只用ENTRYPOINT：特别固定的场景，容器就是干一件事的

ENV - 环境变量

ENV用来设置环境变量，在容器运行时生效。你可以在后续的RUN、CMD等指令中使用这些变量。

常见用法：

  • 设置NODE_ENV=production告诉Node.js这是生产环境
  • 设置PATH添加自定义命令路径
  • 配置应用参数（端口号、数据库地址等）

注意ENV设置的变量会保留在最终镜像里，如果里面有敏感信息（比如密码），别用ENV。应该在运行容器时通过docker run -e传入，或者用Docker Secrets。

初学者避坑指南

前面讲了正确写法,现在聊聊新手最容易踩的几个坑。这些坑我全踩过,能帮你省不少时间。

坑1：构建上下文路径错误

现象：COPY指令报错”no such file or directory”，明明文件就在那儿。

原因：COPY的路径是相对于构建上下文的，不是相对于Dockerfile。

解决办法：

  1. 把文件移到项目目录内
  2. 或者调整构建命令：docker build -f subdir/Dockerfile .（用-f指定Dockerfile位置，最后的点还是上层目录作为上下文）

还有个隐藏坑：如果你在根目录执行docker build .，Docker会把整个目录都发送给Docker守护进程，包括node_modules、.git这些大文件夹。我就遇到过发送了几个GB，等了10分钟才开始构建。

现象：镜像体积巨大，明明代码才几MB，镜像却有几GB。

原因：每条RUN/COPY/ADD都创建新层，即使后面删除文件，前面层的数据还在。

坑3：依赖缓存失效

现象：每次构建都要重装依赖，超级慢。

原因：COPY顺序不对，代码和依赖文件一起复制，每次改代码都触发重装依赖。

Docker的缓存是按顺序的。上面这个写法，只要源代码变了（比如改个注释），COPY那层就变了，后面的npm install也得重新跑。

额外提示：EXPOSE不是必须的

很多教程写了EXPOSE 3000，新手以为不写就无法访问端口。其实EXPOSE只是文档说明，告诉别人这个镜像用哪个端口，不写也能跑。

结论

说了这么多，其实Dockerfile入门就抓住三个关键点：

  1. 理解核心指令：FROM选基础镜像、RUN装东西、COPY搬文件、CMD启动应用，剩下的WORKDIR和ENV是辅助
  2. 搞清楚构建上下文：记住COPY只能访问docker build最后那个点指定的目录，别试图访问上层或绝对路径
  3. 善用缓存机制：把变化少的操作（装依赖）放前面，变化多的（复制代码）放后面，合并RUN指令减少镜像层数

现在就找个自己的小项目试试吧。先写个最基本的Dockerfile，能跑起来就行，不用追求完美。等熟练了，再去学多阶段构建、优化镜像体积这些进阶技巧。

Docker没那么难，关键是动手练。我第一次写Dockerfile报了一晚上错，但搞懂之后发现其实就那么回事。你也能行的。

常见问题

Dockerfile的核心指令有哪些？

6大核心指令：

  • FROM选择基础镜像（必须是第一条）
  • RUN执行命令构建镜像（用&&合并减少层数）
  • COPY复制文件（路径相对于构建上下文，不能用../或绝对路径）
  • WORKDIR设置工作目录（推荐绝对路径）
  • CMD设置容器启动命令（可被覆盖）
  • ENV设置环境变量

还有ENTRYPOINT（固定主命令）、EXPOSE（声明端口，仅文档说明）。

为什么COPY ../config.json会报错？

COPY的路径是相对于构建上下文的，不是相对于Dockerfile。

构建上下文是docker build命令最后那个点(.)指定的目录，COPY只能访问这个目录及其子目录的文件，不能访问上层目录或绝对路径。

解决办法：

  • 把文件移到项目目录内
  • 或调整构建命令：docker build -f subdir/Dockerfile .

创建.dockerignore排除node_modules、.git等大文件夹可加快构建。

如何减少Docker镜像体积？

三个方法：

  • 使用Alpine镜像：
    • 体积5MB vs 完整镜像900MB，相差180倍
  • 合并RUN指令：
    • 用&&串起来，在同一层完成安装、使用、清理
    • 可将镜像从2GB降到200MB，体积减少10倍
  • 创建.dockerignore排除不需要的文件

永远把apt-get update和install写一起，避免使用旧缓存。

如何利用Docker缓存加快构建速度？

关键：把变化少的操作放前面，变化多的放后面。

正确顺序：

  • 先复制package*.json安装依赖
  • 再复制源代码
  • 这样只要package.json不变，依赖层就不会重建
  • 构建速度从5分钟降到10秒（提速30倍）

错误顺序：

  • 先复制所有文件再装依赖
  • 每次改代码都要重装依赖，超慢

CMD和ENTRYPOINT有什么区别？

CMD可以被docker run参数覆盖，ENTRYPOINT不能被覆盖。

使用场景：

  1. 只用CMD：应用服务，可能需要不同启动方式（生产npm start，测试npm test）
  2. ENTRYPOINT+CMD组合：工具类镜像，主命令固定参数不同（如python脚本）
  3. 只用ENTRYPOINT：特别固定的场景

记住：ENTRYPOINT是”做什么”，CMD是”怎么做”。

EXPOSE指令是必须的吗？

不是必须的。EXPOSE只是文档说明，告诉别人这个镜像用哪个端口，不写也能跑。

真正管端口映射的是docker run -p命令。即使Dockerfile没写EXPOSE，docker run -p 3000:3000 my-app也能正常访问。

不过建议还是写上EXPOSE，方便其他人理解镜像使用的端口。

Alpine和slim镜像有什么区别？

Alpine基于Alpine Linux：

  • 体积只有5MB左右，适合生产环境
  • 但用的是musl libc而不是glibc，个别原生依赖可能会报错
  • 完整镜像有900MB，相差180倍

如果遇到奇怪的编译错误，可换成slim版本（如node:18-slim）。

选择原则：优先用Alpine，遇到兼容性问题再换slim。
